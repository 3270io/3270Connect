# Groundskeeper Journal — 3270Connect

## 2026-09-09 - A whole second docs-site build was committed at app/, and two AI-instruction files pointed at it as if it were real
**Finding:** `app/` (53 MB, 61 files) was a self-contained MkDocs build output plus its own `Dockerfile`/`docker-compose.yml` deploying it to nginx and pushing to a private registry (`reg.jnnn.gs/3270_io`), sitting alongside the real docs pipeline (`mkdocs.yml` → `site_dir: site`, deployed to GitHub Pages by `.github/workflows/go.yml`). It even still contained the two demo videos a later commit explicitly said were "removed, along with their 49 MB" — they'd only been removed from `docs/`, not from this forgotten mirror. It had exactly one commit (the initial bulk import) and was never touched again. Despite being fully orphaned from the build/CI/Docker Compose surface, `.github/copilot-instructions.md` and `.github/prompts/ux-ui.prompt.md` both cited `app/static/` as the dashboard's static-assets directory — it never was; that's `templates/static/` per CLAUDE.md. Both files were quietly wrong the whole time and nothing caught it because nothing exercises AI-instruction prose.
**Learning:** A stray top-level directory that *looks* like a live deployment target (has its own Dockerfile + compose file) is not proof it's wired into anything — check `mkdocs.yml`'s `site_dir`, the root compose files, and `.github/workflows/` before trusting a directory's apparent purpose. Also: AI-instruction/prompt files (`.github/copilot-instructions.md`, `.github/prompts/*.md`) are exactly the kind of prose that references paths but is never validated by a build or test, so they drift silently and should be grepped alongside code/CI when checking "is this file genuinely unreferenced."
**Prevention:** When removing an orphaned directory, grep for its path across `.github/**/*.md` too, not just build/CI/deploy configs — a stale mention there won't break anything mechanically, but it will mislead the next agent (human or AI) that reads it as ground truth.

## 2026-09-16 - A duplicate workflow YAML at the repo root fooled a previous agent into "keeping it in sync"
**Finding:** `go-build-mkdocs-docker.yml` at the repo root was a copy of `.github/workflows/go.yml`, present since the initial import commit. GitHub Actions only reads workflows from `.github/workflows/`, so the root copy never ran — but its workflow-like name and content were convincing enough that a later commit (removing the `mkdocs-video` plugin) edited *both* files, treating the root one as a second real workflow needing the same fix. It still drifted out of date on everything else (go 1.20, hand-rolled build steps instead of `build.ps1`, `docker/build-push-action@v4`, no concurrency guard).
**Learning:** A file's *name* and *content* looking like a live CI config is not evidence it's wired in — only its *location* is. For GitHub Actions specifically, only `.github/workflows/*.yml` counts; a workflow-shaped YAML anywhere else is inert regardless of how plausible it looks, and can actively mislead an agent that pattern-matches on "this looks like the CI file" rather than checking where it lives.
**Not acted on this session:** `Jenkinsfile` at the root still builds `dir("app") {...}` and pushes to a private registry, but the `app/` directory it depends on was removed in the 2026-09-09 cleanup above — this pipeline is likely dead too, but Jenkinsfiles are exactly the kind of "might be externally referenced by a real Jenkins server" file this task's guardrails say to leave alone rather than infer from repo state alone.
